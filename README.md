# WTC 3×3: помощник капитана и точный решатель равновесия

**Интерактивное приложение готово:** инструкция по запуску, таблицам с именами,
автосохранению и API контроллера находится в [ASSISTANT.md](ASSISTANT.md).

Публикация и изоляция пользователей в Streamlit Community Cloud: [DEPLOYMENT.md](DEPLOYMENT.md).

Быстрый локальный запуск в уже подготовленном Windows-окружении:

```powershell
.venv-ui\Scripts\wtc-assistant.exe
```

Откройте `http://127.0.0.1:8501`. Приложение работает локально, без сети после
установки зависимостей. Полный набор тестов (ядро + помощник + Streamlit):

```powershell
.venv-ui\Scripts\python.exe -m pytest -q
```

Новый [CSV-шаблон](examples/captain_template.csv) содержит имена прямо в таблице;
[заполненный пример](examples/captain_demo.csv) использует искусственные оценки.
Далее описан вычислительный пакет, на котором построено приложение.

Python-пакет для описанного протокола парингов: два бана, одновременные
выборы щитов и мечей, затем последовательное распределение столов и миссий.
Вычислительный пакет не зависит от UI или сторонних
библиотек во время расчёта. Обе роли команды A рассчитываются независимо.

Нужен Python 3.12 или новее. Обычная установка:

```powershell

.venv\Scripts\python.exe -m pip install -e ".[test]"
```

## Таблица ожидаемых GP

Шаблон Excel: `outputs/01a0e82b-ebf7-7af3-8aa0-c14e14564970/gp_template.xlsx`.
В нём есть лист `GP` с 243 пустыми полями и русскоязычная инструкция с местом
для названий игроков, столов и миссий. Редактируемые поля отмечены жёлтым.
Числа вне диапазона 0–20 подсвечиваются; окончательную проверку делает загрузчик.

Альтернатива для непосредственной загрузки: `examples/gp_template.csv`.
Каждая из 27 строк — сочетание игрока A, игрока B и стола. Заголовок:

```csv
player_a,player_b,table,M0,M1,M2,M3,M4,M5,M6,M7,M8
```

Идентификаторы игроков и столов: `0,1,2`; миссий: `0,...,8`.
В CSV столбцы миссий называются `M0,...,M8`. Заполните **все** 243 оценки
ожидаемых GP **команды A**. Для B значение одного матча автоматически равно
`20 − x`. Команда A сохраняет обозначение независимо от роли Attacker/Defender.
Пустое поле не считается нулём. Повторные/отсутствующие строки, неверные
размерности, `NaN`, бесконечности, логические значения и числа вне 0–20 отвергаются.

Из Excel экспортируйте **лист GP** в CSV UTF-8: разделитель — запятая,
десятичный разделитель — точка. Некоторые региональные настройки Excel дают
точку с запятой: такой файл нужно пересохранить с запятыми. XLSX напрямую
загрузчик не читает. Имена на листе инструкции — справочник для человека,
они не меняют идентификаторы и не участвуют в расчёте.

JSON — вложенный массив `[player_a][player_b][table][mission]`, строго
`3 × 3 × 3 × 9`. `examples/payoffs_demo.json` — заполненные **искусственные**
оценки для проверки, не рекомендации для реального турнира.

Допустимы целые, десятичные числа и строки дробей, например `"123/10"`.
JSON-десятичные числа читаются через `Decimal`, без промежуточного float.
При прямом Python-вводе `float` преобразуется через `str`: `12.3 → 123/10`,
но уже вычисленное `0.1 + 0.2` даст `30000000000000004/100000000000000000`.
Для заранее выполненных вычислений используйте `Fraction` или `Decimal`.

## Публичный API

```python
from random import Random
from wtc_solver import load_payoffs, solve, Session, Stage, sample_action, save, load

payoffs = load_payoffs("examples/payoffs_demo.json")
solution = solve(payoffs, attacker_team="A")
session = Session(solution)
rng = Random(42)

while session.state.position.stage != Stage.TERMINAL:
    # Список акторов берётся ДО записи любого скрытого выбора.
    for team in solution.rules.actors(session.state.position):
        recommendation = session.recommendation(team)
        action = sample_action(recommendation, rng)
        session.act(team, action)

save(solution, "policy.json")
restored = load("policy.json", expected_payoffs=payoffs)
assert restored.get_value(session.history) == solution.get_value(session.history)
public_session = session.export()
restored_session = Session.restore(restored, public_session)
```

`solve(payoffs, attacker_team)` возвращает неизменяемый `Solution`:

| Метод / поле | Точный смысл |
|---|---|
| `get_value(history=())` | Ожидаемый **итоговый** GP при данной публичной истории и оптимальной игре далее |
| `get_recommendation(history, team)` | Все допустимые действия текущего актора, их точные вероятности, стадия, вид действия и значение игры |
| `get_state(history=())` | Состояние, полученное проверенным воспроизведением публичной истории |
| `rules` | Независимый от оценок объект правил для данной роли |
| `nodes` | Неизменяемое отображение канонических будущих состояний в значения/политики; полезно для аудита |
| `statistics` | Статистика расчёта и кэшей; время не входит в правило выбора стратегии |

`history` — последовательность `Event(actions=(...))`. При последовательном
ходе в событии один ID. При одновременном — два ID **всегда в порядке A, B**.
Для щитов ID обозначает собственного игрока; для мечей — выбранного
**чужого** игрока. Передать только один раскрытый одновременный выбор нельзя.
Неверное действие/история вызывает `IllegalAction`, неверные данные — `InvalidData`.

`GameValue` содержит четыре `Fraction`:

- `team_a`: ожидаемый итоговый GP команды A, от 0 до 60.
- `team_b`: `60 − team_a`.
- `accrued_a`: уже зафиксированные **ожидаемые** GP завершённых распределений
  «пара–стол–миссия». Это не результаты реально сыгранных матчей.
- `remaining_a`: ожидаемый вклад ещё не распределённых матчей.

Всегда `team_a = accrued_a + remaining_a`. На терминале `remaining_a = 0`.
В корне `accrued_a = 0`. После неоптимального или конкретного случайно
выбранного хода итоговая условная оценка может отличаться от корневой.
В одновременном узле значение вычислено **до раскрытия обоих выборов**.

`Recommendation.actions` и `probabilities` имеют одинаковый стабильный порядок.
Неоптимальные допустимые действия присутствуют с нулём. Для команды, которая
сейчас не ходит, и на терминале оба кортежа пусты. `value` всегда содержит
оценки обеих команд, а не только запрошенной. `simultaneous` отмечает скрытый
этап. `action_kind` равен `mission`, `table`, `player` или `none`.

`State.matches` содержит назначенные матчи (`a,b,table,mission`),
`position.pairs` — оставшиеся пары в порядке розыгрыша,
`position.tables/missions` — оставшиеся ресурсы, `position.table` — выбранный
для текущего матча стол (либо `-1`). Стол удаляется после выбора миссии.
После последнего назначения остаётся четыре неиспользованные миссии.
До завершения выбора мечей пары ещё не сформированы; `position.shields`
содержит раскрытые щиты на стадии `SWORDS`.

Создавайте состояния через `Rules.initial()/apply()/replay()`, а не вручную.
`Rules.transition(position, actions)` — чистое ядро: возвращает новое будущее
состояние и назначенный этим ходом матч либо `None`. Оно не вычисляет GP.

### Сессии и скрытая информация

`Session.act(team, action)` на последовательном этапе возвращает раскрытый
`Event`. Первый скрытый выбор возвращает `None`, второй атомарно раскрывает
оба. До этого история, состояние и рекомендации не зависят от скрытого
выбора соперника. Повторная отправка своего выбора заменяет его до раскрытия.
`undo()` сначала сбрасывает незавершённые скрытые выборы, иначе отменяет
последнее **целое** раскрытое событие. После отмены можно исследовать любой
другой допустимый ход без нового расчёта.

Публичный `export()` не включает скрытые выборы. Чтобы сохранить всю сессию
посреди одновременного этапа, дополнительно сохраните по отдельности
`export_private("A")` и `export_private("B")`; каждый содержит только собственный
нераскрытый выбор. Восстановление:

```python
resumed = Session.restore(solution, public_json, private_snapshots=(private_a, private_b))
```

Приватные снимки связаны с публичным SHA-256. Не передавайте приватный снимок
одного капитана другому. Файлы не зашифрованы. Будущий сервер должен проверять
авторизацию аргумента `team` и держать контроллер сессии на сервере: библиотека
в одном Python-процессе не служит границей безопасности от доступа к памяти.

`sample_action(rec, rng)` отделён от решателя: общий знаменатель превращает
рациональные вероятности в целые веса, затем вызывается `rng.randrange(n)`.
Здесь также нет округления до float. Передайте собственный RNG для
воспроизводимых сессий.

## Математический метод и выбор одного профиля

Каждое распределение пары, стола и миссии добавляет ожидаемый GP команды A.
На последовательном узле A выбирает максимум `reward + V(child)`, B — минимум.
На одновременном узле строится матрица этих продолжений: строки — действия A,
столбцы — действия B. Выбор щитов даёт 3×3, мечей — 2×2. Каждый элемент уже
учитывает оптимальные последующие решения, включая следующий одновременный
этап. Это обратная индукция по конечной игре с наблюдаемыми раскрытиями.

Матричный решатель перечисляет вершины LP:

```
maximize v
sum(p_i) = 1
p_i >= 0
sum_i p_i M_ij >= v  for every j
```

Перебираются наборы активных ограничений; системы решаются методом
Гаусса–Жордана над `Fraction`, вырожденные системы пропускаются. Все допустимые
оптимальные вершины дедуплицируются. Решение для B получается той же задачей
на `−Mᵀ`; значения прямой и двойственной задач проверяются на точное совпадение.
Поддерживаются также прямоугольные матрицы размером от 1×1 до 3×3 для тестов.

**Правило выбора:** среднее всех различных крайних оптимальных стратегий
отдельно для A и B. В нулевой сумме любая пара оптимальных стратегий образует
равновесие. Среднее сохраняет все действия, положительные хотя бы в одной
оптимальной стратегии: оптимальное множество — ограниченный многогранник,
любая его точка — выпуклая комбинация вершин. Это обеспечивает максимальную
поддержку, но не обязательно максимальную энтропию или равные вероятности.
На последовательных узлах используется равномерная смесь всех оптимальных
действий. Стратегия полностью детерминирована, случайность есть только при
отдельно вызванном семплировании.

Результат — выбранное согласованное равновесное поведение во всех продолжениях,
включая недостижимые при выбранном равновесном пути. Полные контингентные
чистые стратегии игры не строятся. После бана двух миссий порядок банов не
влияет на будущее; после назначения матча его GP становятся общей константой
для продолжения. Такие состояния объединяются по будущим возможностям,
а публичная история и уже назначенные матчи сохраняются отдельно.

Это математическая точность **для введённых оценок**, а не заявление о
точности человеческих прогнозов. Нет Монте-Карло, RL, эвристик или скрытого
перехода к float. Оптимизируется сумма GP, не TP. Бросок кубика не включён.

`matrix_game.solve_matrix(M)` возвращает `MatrixResult`: `value`, `row`,
`column`, число крайних оптимальных стратегий `row_vertices/column_vertices`
и точный `residual = 0`. Диагностика не является численной оценкой допуска.

## Сериализация

Версия формата — `1`. JSON содержит `body` и `sha256` от канонического JSON
`body` (сортированные ключи, без пробелов, ASCII-экранирование). `body` содержит
`version`, `kind` (`solution`, `session`, `private-session`) и `data`.

Политика хранит исходный тензор, его SHA-256, роль, идентификатор правила
`mean-distinct-optimal-vertices-v1`, статистику и записи узлов. Запись узла:

```
[[stage, missions, tables, shields, pairs, selected_table], value, p_A, p_B]
```

Числа в тензоре, значения и вероятности — строки рациональных чисел вида
`"17/3"` или `"10"`. `value` узла — только **оставшийся** GP A. Распределение
неактора пустое. Терминальные узлы не хранятся: их оставшийся GP равен нулю.
Числовые ID стадий заданы `Stage` в `models.py`, от 0 до 9.

`load/loads` проверяют формат, контрольные суммы, заданный ожидаемый тензор,
полноту достижимого графа и все равновесные/Bellman-условия. Они **не ищут
равновесие повторно**. Проверка сертификатов также не перечисляет оптимальные
вершины заново; идентификатор правила выбора фиксирует контракт генератора.
SHA-256 обнаруживает повреждение, но не является подписью против подделки.

## Проверки и независимая верификация

```powershell
python -m pytest -q
python -m wtc_solver.cli verify outputs/policies/attacker_A.json
python -m wtc_solver.cli verify outputs/policies/attacker_B.json
python examples/session_demo.py
```

Тесты включают известные точные матричные игры, вырожденность, доминирование,
неравномерные смеси и максимальную поддержку; каждый сертификат проверяется
по неравенствам для всех чистых отклонений. Правила проверяются отдельно,
включая оба назначения ролей и точное число 3 265 920 терминальных
последовательностей. Есть аналитические тензоры для уникальных банов/столов,
смесей щитов/мечей, равных действий и неоптимальных историй.

`tests/oracle.py` не импортирует производственные правила или оптимизатор:
он полностью перебирает 1 260 распределений для фиксированного паринга и
использует отдельную формулу 2×2. Это сравнение дополняет аналитические тесты.
`verify.py` независимо проверяет сохранённые сертификаты, но использует
публичные правила для построения рёбер; корректность самих правил обеспечивают
отдельные тесты и oracle. Проверяются **все** хранимые узлы полной игры.

Hypothesis генерирует матрицы, полные тензоры и допустимые истории. Число
полных случайных игр ограничено тремя примерами из-за стоимости точного
решения; в них также проверяются перестановка команд и дополнение `20 − x`.
Сериализация проверяется на точное совпадение всех узлов и рекомендаций,
повреждения, несовместимые версии, пропущенные/повторные узлы и чужие тензоры.
Пример проигрывает обе роли, сохраняет, загружает и повторяет сессию с тем же RNG.

## Производительность и ограничения

```powershell
python benchmarks/benchmark.py --output outputs/benchmark.json
```

Бенчмарк вынесен за пределы pytest. Тензор задаётся целочисленной формулой
`benchmark_payoffs()`, его SHA-256 записан в отчёт. Для каждой роли создаётся
отдельный процесс. Первый проход измеряет время решения без инструментирования,
второй — пик Python-аллокаций через `tracemalloc` (он существенно замедляет код).
На обычном Windows CPython дополнительно доступен пик working set процесса;
на MSYS эта метрика может быть `null`. Это явно отличено от Python-аллокаций.
Время запроса — среднее 2 000 корневых запросов, не оценка сети или UI.

`terminal_evaluations` — число вычисленных финальных рёбер после объединения
будущих состояний, а не число всех полных историй. `matrix_nodes` — число
одновременных узлов; `matrix_games_solved` исключает повторы одинаковых матриц.
`cache_hits/misses` относятся к будущим нетерминальным состояниям.
Размер политики измеряется в байтах несжатого JSON.

Измеренные результаты и команды финальной проверки находятся в
`outputs/verification_report.md` и `outputs/benchmark.json`.

Ограничения: только этот фиксированный протокол 3×3 с девятью миссиями;
нет TP, неопределённости оценок, распределений реального счёта, усреднения по
броску кубика или приближённого backend. Очень длинные десятичные входы могут
увеличить знаменатели, время и размер JSON. Изменение тензора требует нового
решения; исследование других допустимых ходов — нет.

## Интерактивный интерфейс

Реализован в `src/wtc_assistant/` на Streamlit с отдельными контроллером, сессией
и импортом/экспортом. Поддерживает имена в исходных данных, обе роли, скрытый
выбор одного капитана, фактические действия соперника, отмену, ветвление истории,
автосохранение и полные переносимые снимки. См. [ASSISTANT.md](ASSISTANT.md).
В вычислительном ядре по-прежнему нет Streamlit, HTTP или состояния браузера.
