# WTC Captain Assistant

Каждая сессия приложения обслуживает **одного капитана**. В облаке несколько
пользователей работают независимо; см. [DEPLOYMENT.md](DEPLOYMENT.md). Наша команда — A внутри ядра,
но интерфейс показывает человеческие имена и «Мы / Соперник». Фактические
действия второго капитана пользователь записывает после их раскрытия.
Все правила и равновесия берутся из существующего `wtc_solver`.

## Запуск

Готовое окружение в этом проекте:

```powershell
.venv-ui\Scripts\wtc-assistant.exe
```

Откройте http://127.0.0.1:8501. Остановка сервера — Ctrl+C в его терминале.
Альтернативная установленная команда: `.venv-ui\Scripts\wtc-assistant.exe`.

На другой машине с обычным CPython 3.12+:

```powershell
python -m venv .venv-ui
.venv-ui\Scripts\python.exe -m pip install -e ".[ui,test]"
.venv-ui\Scripts\wtc-assistant.exe
```

На Linux/macOS используйте `.venv-ui/bin/python`. Для Streamlit на Windows
нужен обычный Windows CPython; старое окружение `.venv` в этом проекте использует
MSYS Python, для которого не доступны некоторые бинарные зависимости Streamlit.
Оба окружения сохранены. Проверенная версия Streamlit — 1.64.0.

Интернет нужен при первоначальной установке пакетов. Приложение не обращается
к внешним API, не использует CDN для прикладных ресурсов и не отправляет GP
на серверы третьих лиц при локальном запуске. В Community Cloud данные
обрабатываются на облачном сервере. Streamlit telemetry отключена. Локальный
launcher слушает только 127.0.0.1. Для публичного сервера используйте режим
`session`, описанный в DEPLOYMENT.md; учётные записи пока не реализованы.

## Исходная таблица с именами

Скачайте шаблон из приложения либо используйте `examples/captain_template.csv`.
Заполненный искусственный пример: `examples/captain_demo.csv`, его JSON-вариант:
`examples/captain_demo.json`. Не используйте демонстрационные числа как оценки
для реального турнира.

CSV содержит 27 строк и 15 столбцов:

```text
player_a,player_a_name,player_b,player_b_name,table,table_name,M0|Миссия 1,...,M8|Миссия 9
```

- `player_a`, `player_b`, `table` — стабильные ID `0,1,2` в своей категории.
- Следующее за каждым ID поле — имя. Для одного ID оно должно совпадать во
  всех строках. Имена могут содержать запятые и кавычки: используйте обычные
  правила CSV или сохраняйте через табличный редактор.
- Девять миссий задаются **в заголовках**: префиксы `M0|…M8|` сохраняйте,
  текст после первого `|` заменяйте на реальные названия.
- В последних девяти столбцах — ожидаемые GP **нашей** команды от 0 до 20.
  Заполните все 243 ячейки. Пустота не равна нулю.
- Имена внутри каждой категории должны различаться (для тёзок добавьте
  фамилию/позывной). Одинаковое имя у игроков разных команд разрешено.
- Кодировка — UTF-8. Принимаются запятые как разделители и точки в числах,
  а также распространённый Excel-вариант с `;` и десятичной запятой.
- Дроби `7/3` допустимы. Конечные десятичные значения экспортируются как
  десятичные числа без округления; другие дроби остаются строками `n/d`.
  В Excel такие нетипичные дроби лучше хранить как текст, чтобы избежать
  автоматического преобразования в даты.

JSON: объект `{"format":"wtc-input","version":1,"names":{...},"tensor":[...]}`.
`names` содержит массивы `players_a`, `players_b`, `tables`, `missions`,
упорядоченные по ID. Тензор — прежний `[a][b][table][mission]`.
Имена находятся **в том же файле**, но не передаются в математический алгоритм.

Прежний безымянный CSV `player_a,player_b,table,M0,...,M8` и голый JSON-тензор
также импортируются. Для них сначала используются стандартные подписи, которые
можно заменить в приложении и сохранить уже в новом формате.

Изменение подписи существующего ID не требует расчёта: редактор имён обновит
снимок и сохранит политику. Это именно переименование, а не перестановка
игроков: оценки остаются привязаны к прежним ID. Перемещая реального игрока на
другой ID, перенесите соответствующие оценки и рассчитайте новую политику.

## Работа на турнире

1. Загрузите таблицу. Приложение проверит размерности, заполнение, числа,
   диапазон GP, уникальность сочетаний ID и согласованность имён.
2. Нажмите «Рассчитать обе роли» или загрузите готовый комплект политик.
   Расчёт запускается только этой кнопкой. Прогресс показывается по двум
   завершённым ролям, без вымышленного процента внутри одного вызова решателя.
3. Просмотрите ожидаемые GP обеих команд при каждой роли и среднее до
   roll-off с вероятностями 1/2. Значения внутри программы — точные `Fraction`.
4. Выберите нашу фактическую роль и начните паринг.
5. На нашем ходу видны **все** допустимые действия, включая вероятность ноль.
   Выберите вручную либо нажмите случайный выбор. Семплирование только
   предлагает действие; запись происходит отдельным подтверждением.
6. На ходе соперника вручную запишите его фактический выбор. Он не выбирается
   автоматически; любое допустимое отклонение от равновесия принимается.
7. На скрытых этапах сначала подтвердите наш щит/меч. Затем дождитесь
   физического раскрытия обоих выборов, отметьте это и введите выбор соперника.
8. Завершите распределение столов и миссий. В итоговой таблице — три матча,
   их GP для обеих команд и сумма 60.

Величины GP — оценки ожидаемых итогов, не гарантия реального игрового счёта.
Строка действия на одновременном этапе оценивает его против **равновесной
смеси** соперника. Самостоятельный чистый выбор может терять гарантию смеси.
После фиксации нашего скрытого выбора верхняя оценка уже учитывает именно
его и явно помечена как ожидание против смеси соперника. После раскрытия
оппонента показывается значение соответствующего фактического продолжения.
На остальных этапах верхняя оценка — оптимальное продолжение публичной истории.

Используется одно выбранное равновесие с максимальной поддержкой из прежнего
решателя. Положительные действия на последовательном этапе равноценны;
на одновременном — оптимальны против равновесной стратегии оппонента.
Проценты округлены методом наибольших остатков до 0,1%, их сумма — 100,0%.
Для очень малой положительной вероятности возможно отображение 0,0%; точная
дробь доступна в явно включаемом диагностическом режиме.

## История и восстановление

«Отменить последнее решение» всегда доступно в боковой панели. Сначала оно
снимает незавершённый собственный скрытый выбор; иначе удаляет последний
публичный ход (оба одновременно раскрытых действия — одно событие).

В истории можно выбрать более ранний этап. Перед возвратом показывается,
сколько следующих событий будет удалено, и требуется подтверждение. Удаляются
**все** последующие события, даже если некоторые формально ещё допустимы:
контекст их выбора уже мог измениться. Все состояния восстанавливаются через
`Rules.replay`. Старые предложения и подтверждения отклоняются по контексту,
включающему сессию, ревизию, историю, роль, собственный выбор, тензор и имена.

При локальном запуске через `wtc-assistant` (`WTC_STORAGE_MODE=local`)
после каждого подтверждения, отмены и переименования автоматически записывается
`outputs/assistant/autosave.json`. Файл заменяется атомарно после записи и
`fsync`. При ошибке диска новое решение не принимается в память. Защита от
устаревшей вкладки проверяет предыдущий digest под блокировкой внутри процесса.
Работайте с одним сервером и одной активной сессией; блокировка между отдельными
процессами сервера не реализована. Автосохранение — один последний паринг;
старые сессии сохраняйте отдельным ручным экспортом.

После закрытия вкладки или сервера нажмите «Восстановить автосохранение».
Оно не восстанавливается молча, чтобы исключить продолжение чужого паринга.
Путь можно задать переменной `WTC_AUTOSAVE_PATH` до запуска.

При прямом запуске `streamlit run streamlit_app.py` по умолчанию используется
облачный режим `session`: автосохранение находится только в памяти текущего
подключения, независимо от других пользователей. После обновления страницы
или перезапуска сервера продолжение доступно через заранее скачанный JSON.
Общий локальный файл в этом режиме не читается и не изменяется.

Полный JSON-экспорт содержит конфигурацию с именами, **обе** готовые политики,
роль, историю и незавершённый **наш** выбор. Дополнительные файлы не нужны,
при восстановлении решатель не запускается. Нераскрытых выборов соперника
приложение никогда не получает. Экспорт нашего капитана не предназначен для
передачи сопернику до раскрытия, поскольку содержит наш скрытый выбор.

Версия формата, версия установленного решателя, правило выбора стратегии,
контрольные суммы, GP, привязки имён и законность истории проверяются при
импорте. Подписи имён при загрузке политики в уже открытую конфигурацию должны
совпадать; исправляйте их отдельным переименованием. Для старых файлов ядра
нужно загрузить обе роли и явно подтвердить привязку имён к их ID.
SHA-256 защищает от случайного повреждения, а не от намеренной подделки.

## API без Streamlit

```python
from pathlib import Path
from random import Random
from wtc_assistant.data import import_data
from wtc_assistant.solutions import calculate
from wtc_assistant.controller import CaptainController
from wtc_assistant.import_export import Autosave, export_session, import_session

config = import_data(Path('examples/captain_demo.csv').read_bytes(), 'input.csv')
bundle = calculate(config)  # два вызова существующего solve
storage = Autosave('outputs/assistant/my-session.json')
captain = CaptainController.start(bundle, attacker_team='A', persist=storage.save)

view = captain.view()
if view.mode == 'own':
    proposal = captain.propose_sample(Random(42))
    # После отдельного подтверждения человеком:
    captain.confirm_own(proposal.action, proposal.context)
elif view.mode in ('opponent', 'reveal'):
    # Только реально раскрытое действие, введённое пользователем:
    captain.record_opponent(view.options[0].id, view.context)

snapshot = export_session(captain.bundle, captain.session)
restored = import_session(snapshot, persist=storage.save)  # не вызывает solve
```

В примере `view.options[0]` — заполнитель для вручную введённого фактического
действия, не стратегия автоматического управления соперником.

| API | Результат/действие |
|---|---|
| `import_data(bytes_or_str, filename)` | Проверенные `Configuration(Payoffs, Names)` |
| `export_csv(config=None)` | Заполненная таблица, либо пустой шаблон при `None` |
| `export_json(config)` | Имена и тензор в одном JSON |
| `calculate(config, progress=None)` | `PolicyBundle` с двумя готовыми решениями |
| `bundle.pre_roll_a` | Точное среднее GP нашей команды до броска |
| `CaptainController.view()` | Типизированные действия, вероятности, значение, пары, ресурсы, публичная история |
| `propose_sample(rng)` | `Proposal(action, context, sampled=True)`; не меняет состояние |
| `confirm_own(action, context)` | Проверить и записать наш выбор; на одновременном этапе держать его отдельно |
| `record_opponent(action, context)` | Записать раскрытый выбор; до нашего скрытого подтверждения запрещено |
| `undo(context)` | Удалить последнее решение/незавершённый выбор |
| `rewind(keep_events, context)` | Оставить указанный префикс публичной истории |
| `rename(names, context)` | Изменить подписи ID, сохранить те же вычисленные стратегии |
| `export_session(bundle, session)` | Полный переносимый JSON |
| `import_session(text, persist=None)` | Проверенный контроллер без перерасчёта |
| `Autosave.save / restore` | Атомарное сохранение и проверенное восстановление |

`DecisionView.mode`: `own`, `opponent`, `reveal` (наш выбор зафиксирован),
`complete`. `options` всегда соответствует действиям ожидаемого участника.
Для оппонента вероятности и альтернативные оценки равны `None`, а не нулю.
`context` обязательно возвращается с каждым подтверждением для защиты от
устаревшего UI. Ни в публичном API контроллера, ни в его snapshot нет поля
для нераскрытого действия соперника.

`DecisionView.value` содержит итоговые `team_a/team_b`, уже назначенный
`accrued_a` и `remaining_a`, все как `Fraction`. Во время `reveal` это значение
условно на нашем уже зафиксированном выборе против сохранённой смеси B;
иначе совпадает с `Solution.get_value(public_history)`.

Единственное расширение математического API —
`Solution.get_action_values(history, team)`: точные оценки каждого действия
по уже сохранённым дочерним значениям. На одновременных этапах оно возвращает
ожидание против смеси противника и худший GP модели для запрошенной команды.
Решатель и правила не переписаны. UI не вычисляет равновесие или payoff.

Модули: `config.py` / `data.py` — ввод; `solutions.py` — расчёт/комплект;
`session.py` — неизменяемая запись; `controller.py` — операции;
`recommendations.py` — типы отображения и округление;
`import_export.py` — файлы; `app.py` — только Streamlit-представление.

## Проверка

```powershell
.venv-ui\Scripts\python.exe -m pytest -q --junitxml=outputs/captain-test-results.xml
.venv-ui\Scripts\python.exe examples/captain_demo.py
```

Прежние тесты ядра сохранены. Новые тесты покрывают обе роли, нулевые вероятности
и реальные отклонения, оба скрытых этапа, возобновление с собственным скрытым
выбором, повреждённые файлы, несогласованные имена, ошибки диска, устаревшие
вкладки, отмену и ветвление. Streamlit проверяется через официальный
[AppTest](https://docs.streamlit.io/develop/api-reference/app-testing/st.testing.v1.apptest):
полный паринг обеих ролей, подтверждение семплирования, старт и отсутствие
автоматического повторного расчёта. Эти тесты не требуют браузера.

Ограничения ядра из README сохраняются: только 3×3, три стола и девять миссий,
модель GP без TP/распределений реального счёта. Загрузка проверяет все узлы
политики и может занимать несколько секунд; во время расчёта Streamlit ждёт
завершения текущей роли. Прямого импорта XLSX и сетевой игры двух капитанов нет.
